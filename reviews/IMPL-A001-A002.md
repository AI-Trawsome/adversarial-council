## A-001 — Codex token capture

### Cause

The runner read `result.turn?.usage`. **That field does not exist in the Codex app-server protocol.** It was never a flaky or best-effort capture that happened to fail; it was reading a field the provider never sends, so it could only ever have been null. Every Codex turn in the T01 pilot recorded `usage: null` for that reason.

The real source was found by instrumenting the notification handler's `default` branch and running one live turn against a throwaway repository. Four notification methods arrive that the runner did not handle, one of which is:

```json
{
  "method": "thread/tokenUsage/updated",
  "params": {
    "threadId": "...", "turnId": "...",
    "tokenUsage": {
      "total": { "totalTokens": 20305, "inputTokens": 19994, "cachedInputTokens": 0,
                 "cacheWriteInputTokens": 0, "outputTokens": 311, "reasoningOutputTokens": 126 },
      "last":  { "totalTokens": 20305, "inputTokens": 19994, "cachedInputTokens": 0,
                 "cacheWriteInputTokens": 0, "outputTokens": 311, "reasoningOutputTokens": 126 },
      "modelContextWindow": 258400
    }
  }
}
```

Usage arrives as its own notification, keyed by thread. `turn/completed` carries no usage field at all.

### Change

`plugins/council/scripts/lib/codex.mjs`

- `createTurnCaptureState()` gains `tokenUsage: null`.
- `applyTurnNotification()` gains a `thread/tokenUsage/updated` case that stores `params.tokenUsage` **verbatim**, and only when `params.threadId` matches the state's own thread — subagent threads report their own usage and must not be billed to the main turn.
- New exported `normalizeTokenUsage(tokenUsage)` projects `tokenUsage.last` (the turn's own usage; `.total` is cumulative for the thread). Returns `null` when the provider reported nothing. There is deliberately no fallback that computes or estimates a count.
- `runAppServerTurn()` and `runAppServerReview()` return `usage` (raw) and `tokens` (normalized).
- `createTurnCaptureState` and `applyTurnNotification` are exported as a test seam.

`plugins/council/scripts/council-runner.mjs`

- New `accumulateUsage()` keeps each call's raw payload in a list, in call order. A list rather than a merged object because a round can bill more than one turn: the malformed-output retry is a second billed call, and the round's cost is both.
- New `accumulateTokens()` sums the normalized projections field-wise. A field the provider did not send stays missing rather than becoming zero — a zero would report a measurement that was not taken.
- New `usageStatusFor()` records `captured`, `missing`, or `not-applicable`. This distinction is the part worth arguing for: a bare `null` cannot separate *"the provider reported nothing"* — a hole in a gating metric — from *"no provider was called"*, which is simply what Arm A is. The pilot could not tell those apart, so a null looked equally like a bug and like normal Arm A operation.
- The stats entry per round is now `{round, side, durationMs, codexCalls, mocked, usageStatus, usage, tokens}`.
- `main()` now runs only when the file is invoked directly, so the suite can import the cost helpers. S3 is a gating criterion; the functions computing it should be assertable without spawning a process or calling a provider.

### Validation

Fifteen new assertions in `scripts/test/protocol-tests.mjs` §13. The payload they drive is the one captured from the live session above, not an invented shape — a hand-written fixture would have proved only that the code reads the field the test author imagined.

What they pin down:

- usage is captured, and the raw payload survives verbatim
- normalization projects `.last`, not `.total`
- **a `turn/completed` payload yields no usage** — this is the regression itself, asserted directly, so that reverting to `turn.usage` fails the suite
- usage from another thread is not attributed to this turn
- absent usage normalizes to `null`, never to zeros; a cumulative-only payload yields no per-turn projection
- a retry's two payloads are both preserved and their counts summed, not overwritten
- a missing field is not counted as zero
- `missing` and `not-applicable` are distinguished
- end to end: a mocked (Arm A) round records `usageStatus: "not-applicable"` and invents no counts

**Live verification.** Unit tests cannot prove the wiring, so one real Codex turn was run end to end after the change:

```json
{"round":1,"codexCalls":1,"mocked":false,"usageStatus":"captured",
 "tokens":{"totalTokens":20226,"inputTokens":19982,"cachedInputTokens":0,
           "cacheWriteInputTokens":0,"outputTokens":244,"reasoningOutputTokens":70},
 "rawTotal":20226,"rawLast":20226}
```

S3 is now computable on the token axis.

## A-002 — Scrubbed full checkouts

Two new harness scripts under `bench/`. They are benchmark harness, not plugin code, and are deliberately committed so a re-run is reproducible from the repository alone.

### `bench/make-scrubbed-checkout.mjs`

```
node bench/make-scrubbed-checkout.mjs --repo <sourceClone> --buggy-sha <sha> --out <dir> --task <id>
```

Exports the tree at the buggy SHA into a freshly initialized repository, then writes a manifest.

**Why blob-by-blob rather than `git archive`:** `git archive` honours `export-ignore` attributes and would silently drop paths, producing a checkout that does not match the tree the manifest claims it matches. Files are written from `git ls-tree -r -z --full-tree` + `git cat-file blob`, preserving mode (including the executable bit) and symlinks.

Scrub properties, per the approved spec:

- fresh `git init`, one commit, message `Initial import`, fixed identity (`Benchmark Harness <harness@localhost>`) and fixed date — so the same tree in yields the same commit SHA out, and the operator's name never enters a reviewer's context
- no original object database, packfiles, alternates, grafts, remotes, tags, extra branches, replace refs, worktrees, or submodule metadata
- reflogs deleted after the import commit
- `git add -A -f` — the `-f` matters: the tree's own `.gitignore` would otherwise skip paths that were tracked in the source repository
- submodule gitlinks excluded and recorded

**Agent-instruction exclusion — countersigned separately as A-002-E1** (consult 002, `reviews/CHATGPT-RULING-014-a002-extension.md`). `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.codex/`, and similar are excluded, because CLAUDE.md is read by Claude and AGENTS.md by Codex — leaving both in place hands each arm repository-authored instructions the other never sees, in exactly the variable the benchmark holds constant. T01's tree ships both plus a `.claude/skills/` entry.

Policy lives in `bench/exclusion-policy.mjs` (version 2), imported by **both** the constructor and the auditor. One module on purpose: an auditor with its own copy of the rules would only ever confirm that two copies agreed.

- Instruction basenames match at **any depth**, not just the root — a nested `CLAUDE.md` governs its subtree.
- Content-blind and path-shaped: nothing inspects what a file says, so there are no task-by-task judgment calls.
- Exclusions record `{path, mode, oid, oidType, bytes, sha256, rule, reason}`. A bare path would say a file called CLAUDE.md went, not which bytes went.
- Directory-level exclusion of `.claude/`, `.codex/`, `.cursor/`, `.windsurf/`, `.aider/`, `.github/copilot/` is **a declared limitation**: it removes everything beneath those paths, including ordinary project source. File-level classification is not reliable — those trees mix skills, prompts, settings, and helpers with no marker separating what an agent reads from what it does not. The declaration is embedded in every manifest as `policy.limitation`, and the auditor reports `declaredLimitation: ABSENT` if it goes missing.

`--keep-agent-instructions` reverses the exclusion; every manifest records which way it went, and the auditor skips the policy checks only when the manifest says instructions were deliberately retained.

**Manifest** (`<out>/../<task>-MANIFEST.json`): source repo, buggy SHA, buggy tree SHA, import commit and tree, harness identity and fixed date, exclusion policy, counts, every exclusion with its reason, and per file `{path, mode, oid, bytes, sha256}`. The blob `oid` recorded from the source tree is what makes the export provable rather than merely plausible.

### `bench/audit-scrubbed-checkout.mjs`

```
node bench/audit-scrubbed-checkout.mjs --out <dir> --manifest <file> [--repo <sourceClone>] [--forbidden-sha <fixSha>]
```

Re-derives everything it checks rather than trusting the constructor: content hashes recomputed, blob ids recomputed with `git hash-object`, file set compared in both directions.

Twenty-six checks in five groups: the isolation property (fix commit unreachable; exactly one commit), no route back to source history (alternates, grafts, reflogs, worktrees, submodule metadata, packed-refs, remotes, tags, branch count, replace refs, stray refs), export fidelity (content hashes, blob ids, tree id cross-checked against the source repo, no missing or extra files), the exclusion policy verified in both directions (A-002-E1: no policy-matched path survives; every exclusion is one the policy independently produces; excluded paths carry blob identity; every source path is exported or recorded as excluded; every policy-matched source path was excluded; policy version matches), and a clean working tree.

`--forbidden-sha` is the decisive one: the maintainer's fix commit must not resolve inside the scrubbed repository. Without it the audit reports that the decisive check did not run rather than passing quietly.

Output is a verdict, counts, and failure reasons — no file contents, nothing about the defect. Safe for a contamination-sensitive orchestrator to read.

### Validation on T01

```
make:  446 files exported, 4 excluded, importCommit c79d98caf92ff90bcbe560c03199c0f52e34c05f
audit: {"verdict":"PASS","checks":26,"failed":0,"filesAudited":446,"excluded":4,
        "policyVersion":2,"declaredLimitation":"present"}
```

Exclusions recorded for T01: `AGENTS.md`, `CLAUDE.md`, `.claude/skills/backport-failed/SKILL.md` (agent instructions), and `vendor/llhttp` (submodule gitlink). The import commit SHA is unchanged from the policy-v1 build, which is the determinism guarantee doing its job.

**Negative tests.** A check that never fails proves nothing. Four were run.

Against the *unscrubbed* T01 clone — the state the pilot would have been in had the full clone gone to reviewers — 8 checks fail including the decisive one:

```
{"verdict":"FAIL","failed":8,
 "failures":["fix commit is unreachable in the scrubbed repo","scrubbed repo has exactly one commit",
             "no reflogs","no packed refs inherited from a source repo","no remotes","no tags",
             "no refs outside refs/heads","no file on disk outside the manifest"]}
```

Three more target the A-002-E1 checks specifically, the last two isolating a single failure each:

| tamper | result |
|---|---|
| an instruction file left in the checkout | FAIL — `no policy-matched path survives in the checkout` (+3 consequential) |
| manifest claims an exclusion the policy does not produce | FAIL — `every exclusion is one the policy independently produces` (1 failure, nothing else) |
| an exclusion recorded without blob identity | FAIL — `excluded paths record blob identity and hash` (1 failure, nothing else) |

The second and third are what the bidirectional requirement is for. Verifying removals alone would pass a scrub that deleted half the repository; verifying justifications alone would pass a scrub that missed an instruction file outright. Neither failure is visible from the other side.
